# Правила ведения ADR

Architecture Decision Records ведутся в каталоге `docs/adr/` с помощью
[`@adrkit/cli`](https://adrkit.dev) (бинарник `adrkit`; глобальная установка
`npm install -g @adrkit/cli`). См. ADR-0001.

## Когда создавать ADR

Создавай ADR для решений, которые:

- меняют архитектуру или разделение ответственности (backend vs team_lead,
  агентские роли, очереди);
- добавляют/заменяют ключевые технологии и инструменты (движки агентов,
  LLM-провайдеры, брокеры, CI-инфраструктура);
- задают процесс разработки (ветки, ревью, тестирование, релизы);
- влияют на безопасность или хранение секретов.

Не создавай ADR для мелких правок, рефакторинга без смены подхода и выбора
имён/путей.

## Команды

```bash
adrkit new "Заголовок решения" --dir docs/adr   # создать запись (status: draft)
adrkit lint                                      # валидация корпуса
adrkit graph                                     # граф зависимостей решений
adrkit queue                                     # очередь proposed-записей
adrkit approve 0002 --by @user                   # одобрение
adrkit object 0002 --by @user --summary "..."    # возражение
adrkit resolve 0002 --objection 1 --by @user     # снятие возражения
adrkit accept 0002 --by @user                    # принять (proposed → accepted)
```

## Процесс

1. Решение обсуждается, затем создаётся запись: `adrkit new "..."`.
2. Заполняются секции: Context, Decision, Options considered (минимум две
   реальные альтернативы, включая "ничего не делать"), Trade-offs,
   Consequences (обязательно "How we would know this was wrong"), Action items.
3. Записи ставится `status: proposed` и отправляется на ревью
   (`adrkit queue` → `approve`/`object`).
4. После кворума одобрений и без открытых возражений — `adrkit accept`.
5. Изменение ранее принятого решения делается новым ADR с отношением
   supersedes к старому; старый не редактируется.

## Обязательные требования

- Каждая запись проходит `adrkit lint` без ошибок перед коммитом.
- Frontmatter: корректные `id`, `title`, `date`, `tags`, `affects` (пути,
  которых касается решение), `status`.
- В `Options considered` — только настоящие альтернативы, не соломенные чучела.
- В `Consequences` — честные минусы и измеримый признак ошибочности решения.

## Связь с правилами и документацией

- Значимые архитектурные решения фиксируются в ADR, краткое текущее состояние
  отражается в `AGENTS.md` и `.agents/rules/architecture.md`.
- Если ADR меняет процесс или структуру — обнови соответствующий файл правил
  и `AGENTS.md` в том же коммите (см. `documentation.md`).
- При изменениях по путям из `affects` проверяй, не устарело ли решение:
  `adrkit explain <path>`.
