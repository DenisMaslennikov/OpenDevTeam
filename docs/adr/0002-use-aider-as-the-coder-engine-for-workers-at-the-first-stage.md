# ADR-0002: Use aider as the coder engine for workers at the first stage

## Context

Worker-агент в режиме `coder` должен вносить изменения в код проекта по
задачам из очереди. Нужен CLI-инструмент, который умеет работать в репозитории
из командной строки (headless, внутри Docker-контейнера агента), выполнять
команды по инструкции и откатывать неудачные правки. Это решение только для
первого этапа (MVP) — на следующих этапах движок может быть заменён, поэтому
он выведен в конфигурацию (`CODER_ENGINE`).

## Decision

Будем использовать [aider](https://aider.chat) как движок внесения правок в
код для worker-агентов на первом этапе. Worker в режиме `coder` вызывает aider
headless внутри своего контейнера (Docker-in-Docker), передавая ему задачу,
LLM-ключ и целевой репозиторий. Движок задан по умолчанию в переменной
`CODER_ENGINE` (`docker/worker/.env`), так что замена на другой инструмент не
потребует изменения кода агента.

## Options considered

### Option A: aider (chosen)

| Dimension | Assessment |
|---|---|
| Headless-режим | Да: `aider --message`, автокоммиты, `--yes` для неинтерактивной работы |
| Git-нативность | Работает поверх git, делает коммиты, умеет `/undo` откат |
| Управление контекстом | Repo-map, добавление файлов в контекст, поддержка больших репо |
| LLM | Работает через LiteLLM-совместимые OpenAI/Anthropic API |
| Зрелость | Активный OSS-проект, широко используется в агентских пайплайнах |

### Option B: OpenHands / проприетарный агентский SDK

**Pros:** более богатые агентские циклы (планирование, инструменты).
**Cons:** тяжеловесный рантайм для пода воркера; избыточен для MVP, где цикл
управляет сам LangGraph-агент в `packages/agents/worker`.

### Option C: Свои LLM-диффы (без специализированного инструмента)

**Pros:** полный контроль, минимум зависимостей.
**Cons:** медленно разрабатывать с нуля патчинг, откат, управление контекстом
репозитория; качество правок ниже, чем у отлаженного инструмента.

### Option D: Do nothing — кодер пишет патчи вручную через LLM

**Pros:** никакой зависимости.
**Cons:** тот же вариант C, отложенный; блокирует MVP.

## Trade-offs

- aider — ещё один слой поверх LLM: свои промпты и токен-расход, сложнее
  прогнозировать стоимость задачи.
- Зависимость от формата работы aider (автокоммиты, стиль правок) — ревьюерам
  придётся учитывать это в правилах.
- aider не является официально рекомендуемым в связке с LiteLLM proxy —
  потребуется проверка совместимости при первом запуске.

## Consequences

- Плюсы: быстрый запуск MVP кодера без собственной реализации патчинга;
  откат неудачных правок через git/aider.
- Минусы: два уровня LLM-конфигурации (агент и aider) в одном поде; возможные
  сюрпризы совместимости с proxy.
- **How we would know this was wrong:** если доля задач, которую aider не
  может довести до валидных тестов, устойчиво высока, или поддержка proxy
  заблокирует работу — меняем `CODER_ENGINE` на альтернативу (открытый вариант
  ADR-0001 не требует).
- Revisit if: начинается второй этап развития воркеров или выходит финальная
  оценка стоимости/качества aider-правок.

## Action items

2. [ ] Реализовать вызов aider в режиме `coder` (`packages/agents/worker`).
3. [ ] Прописать `CODER_ENGINE` по умолчанию в `docker/worker/.env.example`.
